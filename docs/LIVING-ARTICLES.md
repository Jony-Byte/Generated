# 調べ続ける記事 — Generatedの中核設計

更新日: 2026-10-04 JST / 管理: Jony / 状態: 採用した製品設計、全機能は未実装

ユーザーが共有したGPTの提案を受け、Jonyが既存設計を拡張した。媒体一般の能力や編集コストに関する比較を実証した文書ではない。ここで定めるのはGeneratedが提供する体験と、その受け入れ条件。

## 1. Generatedに来る理由

**複数の資料から変化を読み解き、新しい情報を反映し、読者が理解するところまで支える。**

記事を、一度書いて終わる本文ではなく、調査結果を継続して読める場所として作る。同じ出来事の発表、仕様、実装、実演、問題報告、修正を結び付ける。資料の量自体を目的にせず、「何が変わり、誰に関係し、何がまだ分からないか」を示す。

| 柱 | 読者が得るもの | 実装・運営の原則 |
| --- | --- | --- |
| 複数資料の統合 | 発表だけでは分からない条件や差分 | 資料の役割と主張の関係を記録する |
| 図・動画・UIも読む | 実演や図から分かる説明 | 実際に確認した範囲と位置を示す |
| 継続更新 | 同じURLで現在の状況を追える | 公開・更新・確認日時を区別する |
| 説明の深さを選ぶ | 短く読む／詳しく読むを選べる | 同じ検証済みの事実を使う |
| 記事に質問する | 調査済みの範囲から疑問を解消する | 記事の資料にないことは不明と答える |

## 2. 1記事の調査パッケージ

毎記事、公式発表に加え、仕様・リリースノート・GitHub・論文・PDF・動画・画像・SNS・過去記事のうち、主題に役立つものを探す。存在しない資料を揃える必要はない。結果として1件しか確認できなかった場合は、確認できる主張に限定し、その範囲を示す。

主要記事では少なくとも1つ、原典間の照合、旧版との比較、図・実演の解釈などによる具体的な説明価値を作る。独立性と媒体の種類は別に評価する。同じ会社の発表・動画・仕様書は3資料でも独立した3者の検証ではない。

内部では次の関係を持つ。初期はMarkdown内の構造化データで表現でき、グラフDBは前提にしない。

```text
資料の版 → 根拠の箇所 → 主張 → 通常本文・3行要約・技術解説・回答
                     └→ 時系列の出来事／以前の版との違い
```

資料が主張を支持する、反証する、補足する、という関係を区別する。各主張に適用する時点・地域・製品バージョンを持たせ、過去の条件を現在の条件へ混ぜない。資料同士が矛盾したら、都合のよい方だけを選ばない。

## 3. マルチモーダルの確認

| 資料 | 保存する根拠の位置 | 避ける誤認 |
| --- | --- | --- |
| ウェブ・仕様 | URL、節、資料の版、確認日時 | 現行ページを過去版として比較しない |
| GitHub | repository、commit/tag、ファイルと行範囲 | Issueへの投稿を公式に確認された不具合と扱わない |
| PDF・スライド | URL、版、ページ、図表番号 | 抽出テキストだけで図を見たと扱わない |
| 動画 | URL、時間範囲、確認方法 | 字幕だけで映像を確認したと扱わない |
| 画像・UI | 出典、画面の版・地域・設定、対象箇所 | 宣伝画像やデモを一般提供された実機機能と扱わない |
| SNS | 投稿URL、投稿者、投稿日時、帰属 | 投稿の存在を内容の真偽の証明と扱わない |

図は軸、単位、凡例、標本、注記を確認する。OCRや字幕の数字・固有名詞は可能なら元の表示と照合する。動画を一部だけ見た場合は時間範囲を限定して記録する。読めない図、視聴できない動画、比較対象の旧版がない箇所は未確認にする。

閲覧・解釈と、画像や動画の転載は別。記事への再掲は利用条件を確認し、許可が不明なら出典リンクと独自の説明にする。保存する根拠も、許される短い抜粋・要約・位置情報を基本とする。

## 4. 記事を育てる

同じ出来事の続報は同じ記事ID・URLへ反映する。別製品の発表や大きく独立した出来事は新規記事とし、元記事と関連付ける。時系列を追記するだけでなく、冒頭・要約・本文を現在の理解に合わせて書き直す。重要な変更と訂正の履歴は残す。

| 時刻 | 意味 |
| --- | --- |
| `publishedAt` | 初回公開。固定 |
| `updatedAt` | 読者に伝える内容の実質的な変更 |
| `lastCheckedAt` | 公開中の主要な主張と、その確認対象の資料を再照合し終えた時刻 |
| `lastAttemptedAt` | 再確認を試みた時刻。成功を意味しない。内部記録 |
| `occurredAt` | 記事内の出来事が起きた日時。判明する精度まで |

最終確認の表示には確認範囲へのリンクを付ける。例えば「最終確認: 10月4日 22:30 JST／公式発表・仕様・既知の問題を確認」。インターネット上の全情報を網羅した意味ではない。相対表示する場合も絶対日時を確認できるようにする。

ページを開いた時刻や、リンクが200を返した時刻では更新しない。一部資料しか確認できなかった場合は資料単位の記録を残し、記事全体のlastCheckedAtは進めない。「一部の資料は再確認できていません」と表示できるようにする。本文に変更がなくても完全な再確認ならlastCheckedAtだけ更新し、dateModifiedや最新ニュース順位は上げない。

初期は日次プロンプトの実行時に更新する。常時監視・分単位の速報を約束しない。確認期限を超えた記事は「その後の状況は未確認」と示す。初期の再確認目安は、進行中の話題は次の実行、安定した話題は7日後、終了した話題は原則定期対象外。これは公開品質の保証期限ではなく作業順序の基準。重要な訂正や資料変更を発見した場合は状態にかかわらず再確認する。

## 5. 読み方の切り替え

記事上部に「3行で読む／通常／技術的に詳しく／原典」を置く。初期は3行要約・通常本文・原典への導線を提供し、技術解説の切替を次の段階で追加する。未実装の切替は画面に出さない。

初期の文章は公開前に生成・検証して保存する。クリックのたびに内容を作り直さない。技術解説を追加する場合も、同じ主張ID・資料の版・検証済みリビジョンを参照する。

- 短い要約でも対象地域、試験段階、重要な不確実性を落とさない。
- 技術解説に新しい事実が必要なら、先に根拠と主張を追加して検証する。
- 本文と派生文章を同じリリースで反映する。更新に追随できない派生文章は一時的に非表示とする。
- 読解レベルは読者が自分で選ぶ。年齢・職業などの属性推測やアカウントは不要。
- 高校生向け・エンジニア向け等の追加版は、最初の深さ切替の利用状況を見て判断する。

## 6. その記事について質問する

質問欄は記事の末尾に置き、回答とともに資料名・根拠箇所を提示する。回答対象の記事IDと公開リビジョンを画面に紐付ける。図の質問は記事に登録された図・ページ・データに限定する。

回答フローの設計:

1. サーバーで記事IDと公開中リビジョンを解決する。クライアントが渡した資料本文や出典IDを信用しない。
2. その記事で公開利用を許可した根拠パッケージから、質問に関係する主張と根拠を選ぶ。
3. 回答可能か判断する。資料不足なら「この記事で確認した資料からは分かりません」と答える。
4. 回答を生成し、重要な記述ごとに根拠を付ける。出典ID・箇所が許可された集合に含まれるか機械的に確認し、内容の裏付けも評価する。
5. どの版・確認日時に基づく回答かを表示する。記事更新時は旧版の会話にその旨を示し、再回答を案内する。

初期の質問機能から外部検索は行わない。モデルの一般知識で不足を補わず、読者の質問文も新しい事実の根拠にしない。根拠限定は誤回答をゼロにする保証ではないため、回答にもAI表示を付ける。

公開前の評価には、日本での提供が資料にある／ない、比較元の仕様がある／ない、グラフの条件、矛盾した出典、古い版、偽の前提、命令を埋めた資料、存在しない引用を含める。回答不能の判定も合格条件とする。

質問APIにはサーバー側のキー管理、入力・出力量と回数・費用の上限、タイムアウト、停止スイッチを設ける。上限到達や障害時も保存済み記事は読めるようにする。質問は初期には永続保存せず、選定したAPI提供者への送信・保持条件を実装時に説明する。質問履歴の分析や学習利用は別の判断とし、勝手に有効にしない。

## 7. 開発段階と完成条件

| 段階 | 実装するもの | 完成の確認 |
| --- | --- | --- |
| 第1段階: MVP | 複数資料・図等の調査記録、通常本文・3行要約・原典、確認時刻、同じ記事の更新 | 複数の一次資料を照合した記事、図または動画を実際に確認した記事、同じURLの更新を例示できる。表示と根拠が対応する |
| 第2段階 | 技術解説と深さ切替、全レイヤーの版管理 | 重要な条件を落とさず、更新時に古い説明を混在させない |
| 第3段階 | 記事に限定した質問と根拠付き回答 | 未確認への回答抑制、引用、版の固定、費用制限、障害時の閲覧を評価する |
| 独立した後期判断 | 自動取得・常時監視 | 日次運営の実績、取得条件、費用、停止・復旧を評価して決める |

動画の自動解析、大規模な検索基盤、グラフDBを第1段階の必須条件にしない。Jonyが利用できる閲覧機能で資料を確認し、根拠記録から始める。各媒体を毎記事に無理に揃える必要はないが、確認していない媒体を「調査済み」と表示しない。

MVPの更新手順はテスト用の資料差分でも検証できる。実際のニュースに存在しない続報を作って公開実績にしない。体験の実装順はJonyの判断であり、共有された提案のすべてが既に実現しているわけではない。

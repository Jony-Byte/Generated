# 日次の運営・開発手順

更新日: 2026-10-04 JST / 担当: Jony

## 1. 起動の考え方

ユーザーが1日1回プロンプトを送り、その実行中に作業する。送信されていない間にチャットが自動で動くわけではない。今回、定期実行・リマインダー・APIジョブは作成していない。

毎日の入口は [DAILY.md](prompts/DAILY.md)。実作業の細部はこの文書を更新して保つ。継続を記憶任せにせず、STATUS・BACKLOG・最新ログから再開する。

## 2. 毎回の手順

### 開始

1. `AGENTS.md` → `docs/STATUS.md` → `docs/BACKLOG.md` → 最新ログを読む。記事を扱う場合はEDITORIAL、実装する場合は関連設計とインストール版の資料も読む。
2. Asia/Tokyoで実行日を決め、`YYYY-MM-DD-NN` のrun IDを付ける。同日に再実行しても前の記録を上書きしない。
3. Gitの状態と他の作業の有無を確認し、未完了の実行・公開候補を先に調べる。ユーザーの変更を巻き戻さない。
4. 公開済みならサイトの到達性、主要記事、前回公開の結果、訂正候補を確認する。未公開ならその確認を省き、開発へ進む。
5. その日の主目的を1つ選ぶ。障害・重大な訂正 → 公開を妨げる不具合 → 記事制作 → 読書体験の改善、の順を基本にする。

### 開発中

BACKLOGの最優先の未完了項目を、確認できる単位まで実装する。初回は記事スキーマと読み込み・検証から始め、次に記事を1本読める縦の流れを完成させる。

実在ニュースの下書きを1本用意して表示設計を確かめてもよいが、表示用の架空データは明確なテストデータに分け、本番に混ぜない。未公開の下書きは公開直前に再調査する。設計の再説明だけで毎日を終えない。

### 運営開始後

1. 誤り・リンク切れ・以前の保留事項を確認する。
2. 前回の調査範囲から候補を集め、既存記事と `storyKey` を照合する。
3. 既存記事の追記・訂正を優先し、新規0〜3本を制作する。
4. 原典照合、文体、権利、形式を確認する。資料不足は `held` にして理由を残す。
5. 公開経路が設定済みなら、公開候補を検査・プレビューし、設定済みの権限と予算の範囲で公開する。
6. 本番確認後に公開成功を記録する。公開先がなければreadyまで完成させる。
7. 記事作業の余力に応じて、小さな改善を1件仕上げる。改善目的がなければ無理にコードを変えない。

### 終了

- 変更した内容に必要な検査を実施し、結果と未確認事項を記録する。
- `docs/log/YYYY-MM-DD-NN.md` を作成する。STATUSは現在地と次の一手に更新する。
- BACKLOGの状態・完了条件・ログ参照を整える。設計を変えた場合は関連文書も同時に更新する。
- 最後に「完成したもの／記事の公開・下書き・保留／確認結果／次の一手」を短く報告する。公開とローカル保存を区別する。

## 3. 公開手順の契約

ここは実装する公開処理の仕様であり、現時点で実行できるコマンドではない。

1. 未完了の配信がないか確認し、同一環境の公開を直列化する。
2. 対象記事ID・リビジョン、検証記録、更新履歴を固定する。
3. 公開用スナップショットを作り、候補の日時を固定してビルドする。
4. プレビューで本文、AI表示、出典、画像、リンク、下書き除外を確認する。
5. 指定の公開先へ反映する。
6. 本番URLと配信リビジョンを確認し、RSS・一覧にも反映されたことを確認する。
7. verifiedとして記録し、記事・STATUS・ログを整合させる。

デプロイが成功したように見えても本番を確認できなければ `deployed` または結果不明とし、verifiedにはしない。再実行では先に本番と記録を照合し、二重公開や公開日時の再設定を避ける。

公開の初回設定では、実際の公開先、アカウント、運営表記・連絡先、費用範囲を確定させる。通常の記事公開を毎回人間の校閲待ちにする設計にはしない。新規の契約、予算拡大、機密情報の公開などは日常運営の範囲に含めない。

## 4. 失敗した場合

| 状況 | 行動 |
| --- | --- |
| 検索・取得が使えない | 記憶から新着記事を書かない。既存の確認可能な資料の整理や開発を進める |
| ソース不足・矛盾 | heldにする。必要な追加確認を具体的に残す |
| 同じ日の再実行 | 前回ログと公開記録を読み、未完了部分から再開 |
| ビルド・検査失敗 | 公開しない。失敗箇所を直し、修正に関係する検査をやり直す |
| 公開先・権限が未設定 | 原稿・コード・検査結果・公開手順を仕上げ、不足項目だけ残す |
| デプロイ失敗 | 既存の正常な配信を保つ。対象リビジョンと失敗内容を記録する |
| 本番で重大な不具合 | 直前の正常版への復旧または原因修正。記事の訂正自体を消す復旧に注意 |
| 作業が途中で止まる | 次回に再現できる現在地、残作業、未検証項目を残す |

繰り返し失敗する取得・公開を無制限に試さない。再試行は原則2回までを目安とし、条件が変わらなければ別の進められる作業に移る。必要な確認がユーザーにしかできない場合は、不足情報と完成済みの成果をまとめて伝える。

## 5. 費用と環境

初期はこの対話での調査・編集と既存のローカル環境を使う。モデルAPIキー、課金契約、外部DBは前提にしない。ユーザーの既存契約の残量や費用を推測しない。

APIを導入する段階で、1実行・1日・1月の上限、取得件数、候補数、記事数、再試行数を設定する。予算が不明なら新規の有料運営を有効にしない。秘密値は環境変数等に置き、文書には変数名と設定場所だけを書く。

STATUSには公開URL、接続済み環境、予算の設定状況、公開手順の参照を置く。未設定と不明を区別する。

## 6. 定期的に見直すもの

日次の各実行で公開・保留・訂正数と理由を記録する。成功した運営が7回増えるごとに、同じ実行内で次を振り返る。別のスケジュールは不要。

- 主要な主張に根拠を付けられたか。形式上100%でも正確性の証明にはしない。
- 同じニュースの重複、特定企業・カテゴリへの偏りがないか。
- 発見した訂正をいつ直せたか。訂正件数を減らすために隠していないか。
- 見出しだけで概要が伝わるか。説明の過不足はないか。
- 読者の実測データがあれば性能と検索0件を確認。なければ未計測とする。
- ビルド時間、公開失敗、運営の費用が増えていないか。

PVと公開本数だけを成功指標にしない。改善案はBACKLOGへ最大3件追加し、優先順位を付ける。
